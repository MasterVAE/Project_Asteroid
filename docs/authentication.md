# Регистрация и единый API

Браузер и Python используют один обработчик команд, одинаковые поля запросов,
результаты и ошибки. HTTP: `POST /api`; игровые запросы также работают по `/ws`.
Регистрация и операции аккаунта идут через HTTP. Перед каждым игровым запросом
сервер проверяет действительность сессии или API-ключа, независимо от транспорта.

## Запуск на сервере

Установите зависимости и пересоберите приложение:

```sh
sudo apt update
sudo apt install build-essential pkg-config libboost-all-dev libssl-dev libsqlite3-dev
make
ASTEROID_PUBLIC_ORIGIN=https://46.173.218.137 ./build/app world.json
```

`ASTEROID_PUBLIC_ORIGIN` — точный origin без завершающего `/`: схема, адрес и,
при нестандартном порте, порт. В systemd задайте его через `Environment=`.
Приложение слушает только `127.0.0.1:8080`. В Nginx сохраните передачу `Host`,
`X-Forwarded-Proto`, `X-Real-IP`, `Upgrade` и `Connection`, настроенную для HTTPS/WSS.
`Host` должен сохранять нестандартный публичный порт, если он используется.
Обычный `https://46.173.218.137` работает с текущим `proxy_set_header Host $host`.

Для macOS: `brew install boost openssl sqlite pkg-config`, затем `make`.

Аккаунты, сессии и ключи сохраняются в `data/auth.sqlite3`. Настройка
`ASTEROID_AUTH_DB=/absolute/path/accounts.sqlite3` задаёт другой путь. Храните БД
на постоянном диске и делайте защищённые резервные копии; SQLite может использовать
соседние файлы `-wal` и `-shm`. База и её содержимое не входят в git.

Локальная разработка требует явного включения HTTP:

```sh
ASTEROID_PUBLIC_ORIGIN=http://127.0.0.1:8080 ASTEROID_DEV_AUTH=1 ./build/app world.json
```

Открывайте ровно этот адрес. Такой режим разрешён только для `localhost:8080`
и `127.0.0.1:8080`. На публичном сервере оставьте HTTPS и не задавайте DEV_AUTH.

## Вход на сайте

Откройте публичный HTTPS-адрес и нажмите «Создать аккаунт». Логины регистронезависимы:
3–32 латинские буквы, цифры, `_` и `-`. Пароль — минимум 12 байт (форма требует
12 символов), максимум 1024 байта. После регистрации вход выполняется сразу.
Перезагрузка страницы восстанавливает сессию. Выход отзывает текущую сессию и
закрывает связанные WebSocket-соединения. Другие сессии остаются активными.

Сессия действует 24 часа. В production используется cookie
`__Host-asteroid_session; Secure; HttpOnly; SameSite=Strict; Path=/`.
JavaScript не читает токен; localStorage/sessionStorage для секретов не используются.
Браузер работает с API того же origin. Параметр `?server=` больше не переключает
сайт на чужой сервер: для другого сервера откройте его собственный сайт.

ID аккаунтов — положительные целые числа, начиная с 1. `SERVER_USER_ID = 0`
зарезервирован для сервера и не является аккаунтом игрока. База запрещает вставку
и изменение ID на 0 или отрицательное значение; ограничения добавляются также к
существующим базам. Ключи и сессии с таким user_id не проходят авторизацию.
Если в старой базе уже есть аккаунт с ID <= 0, запуск остановится с ошибкой:
его нужно перенести на положительный ID с учётом всех связей. Автоматического
удаления или перенумерации аккаунтов нет. Проверка: `make test-auth-ids`.

## Principal и владелец объекта в C++

`Principal` — неизменяемая идентичность пользователя: `user_id` и `username`.
В реестре одного мира каждому аккаунту соответствует ровно один объект. Его
нельзя копировать или перемещать. `AuthContext` описывает конкретную авторизацию:
он содержит `const Principal* principal`, `credential_id` и `is_session`.
Разные сессии и API-ключи одного аккаунта дают один и тот же указатель Principal.

Реестр принадлежит `World`, загружается из БД при создании `AuthStore` и дополняется
при регистрации. Объекты реестра не удаляются при logout или отзыве токена, а их
адреса не меняются при росте контейнера. `AuthStore` получает реестр явно:

```cpp
AuthStore auth(database_path, world.GetPrincipals());
```

После успешной авторизации можно сохранить указатель в объекте мира:

```cpp
const auto context = auth.Authenticate(token);
if (!context) throw ApiError(401, "AUTH_REQUIRED", "Войдите в аккаунт.");

const Principal* principal = context->principal;
const auto entity_id = world.CreateEntity(principal);

// Для доступа к Entity и изменения owner держите mutex мира.
std::lock_guard<std::mutex> lock(world.GetMutex());
Entity* entity = world.GetEntities().at(entity_id);
entity->owner = principal;
// Обратный поиск возвращает тот же объект:
assert(world.GetPrincipals().Find(entity->owner->user_id) == entity->owner);
```

`AuthStore::GetPrincipal(user_id)` также возвращает канонический указатель или
`nullptr`, если аккаунт неизвестен. Для сервера используйте `Principal::Server()`;
владелец новых объектов по умолчанию — сервер с ID 0. `World::CreateEntity` сам
берёт mutex: вызывайте его вне существующей блокировки мира. Метод отвергает
`nullptr` и владельцев из чужого реестра.

Entity хранит невладеющий `const Principal*`. Не удаляйте Principal вручную.
Указатели игроков действуют до уничтожения World, включая период после уничтожения
AuthStore. В БД/файлы нужно сохранять `owner->user_id`, а после перезапуска получать
указатель из загруженного реестра. Адреса памяти между запусками не сохраняются.
Не меняйте ID/логины аккаунтов напрямую в SQLite при работающем сервере.

`Principal` не подтверждает право выполнить запрос: для каждой команды по-прежнему
проверяется живой `AuthContext`. Поле `owner_id` в ответах карты и объектов — ID
владельца. Команда `create_craft` создаёт корабль текущего пользователя через общий
диспетчер HTTP/WS с сессией или API-ключом. Владельцем становится аккаунт,
которому принадлежит сессия или ключ; переданный клиентом `owner_id` игнорируется.

Проверка стабильности указателей, параллельных сессий, logout/отзыва, роста реестра
и создания корабля: `make test-principals`.

В разделе «API-ключи» создайте отдельный ключ для бота, подтвердив пароль.
Ключ показывается полностью только один раз, действует 1–365 дней и имеет доступ
к чтению игры, созданию и полётам своих кораблей (`game:read game:move game:create`),
но не к управлению аккаунтом или другими ключами. Это относится и к ранее выданным ключам.
Одновременно допускается до 20 действующих API-ключей. Их можно отзывать отдельно;
выход из браузера не отзывает ключи. Для прекращения работы бота отзовите его ключ.

## Одинаковые методы SDK

| Метод | Назначение |
|---|---|
| `register(username, password)` | Создать аккаунт и браузерную/клиентскую сессию |
| `login(username, password)` | Войти; текущая переданная сессия заменяется |
| `me()` | Получить профиль |
| `connect()` / `disconnect()` | Открыть / закрыть игровой WebSocket |
| `getMap()` / `getEntity(id)` | Прочитать карту / объект |
| `getMyEntities()` | Получить объекты текущего пользователя: `{"entities": [...]}` |
| `createCraft()` | Создать свой корабль с сессией или API-ключом |
| `flyTo(entity_id, x, y)` | Задать курс своего корабля; доступно с сессией и API-ключом |
| `createApiKey(name, password, expiresDays=30)` | Выпустить ключ после подтверждения пароля |
| `listApiKeys()` / `revokeApiKey(id)` | Список / отзыв собственных ключей |
| `logout()` | Отозвать текущую сессию (для API-ключа используйте `disconnect`) |

В JS методы асинхронные, в Python — синхронные. Игровые методы используют
WebSocket при подключении, иначе HTTP. Новые игровые команды добавляются в один
диспетчер `backend/src/api.cpp`, а не в два отдельных обработчика клиентов.

Запрос полёта: `{"type":"request","request_type":"fly_to","entity_id":111,"x":0,"y":0}`.
Ответ содержит состояние корабля; команда не ждёт прибытия. Корабль разгоняется,
тормозит и останавливается у цели. Запрос к чужому кораблю возвращает 403.
В браузере выберите свой корабль на карте или в меню, укажите X/Y в карточке
и нажмите «Лететь к координатам».

```python
ships = api.getMyEntities()['entities']
if ships:
    api.flyTo(ships[0]['id'], 0, 0)
```

В JS: `await api.flyTo(shipId, x, y)`. В консольном Python-клиенте: `fly <id> <x> <y>`.

### Python

```sh
python3 -m pip install -r frontend/python/requirements.txt
```

Импорт модуля не запускает сеть или консольный ввод:

```python
import os
from frontend.python.asteroidAPI import AsteroidAPI

api = AsteroidAPI('https://46.173.218.137', api_key=os.environ['ASTEROID_API_KEY'])
print(api.me())
api.connect()
try:
    print(api.getMap())
    print(api.getMyEntities()['entities'])
    print(api.getEntity(1))
finally:
    api.disconnect()
```

Для небольших скриптов, как `frontend/python/game.py`, достаточно
`api = AsteroidAPI(); api.connect(); game_map = api.getMap()`.
Без явных аргументов клиент читает ключ из `ASTEROID_API_KEY`, а адрес — из
`ASTEROID_SERVER` (по умолчанию `https://46.173.218.137`).
`getMap()` возвращает обычный словарь: список объектов — `game_map['entities']`.
`connect()` возвращает сам клиент. Соединение можно закрывать автоматически:

```python
from frontend.python.asteroidAPI import AsteroidAPI

with AsteroidAPI() as api:
    game_map = api.getMap()
    print(game_map['entities'])
```

Для локальной разработки задайте `ASTEROID_SERVER=http://127.0.0.1:8080`.
Вместо ключа можно вызвать `api.login(username, password)` перед `connect()`.
Сетевые и серверные ошибки доступны как `APIError` с полями `code` и `status`;
при потере соединения вызовите `connect()` повторно. Запросы автоматически
не повторяются, чтобы будущие команды изменения мира не выполнялись дважды.

Ключ задавайте через защищённое окружение процесса или хранилище секретов,
а не в исходниках, URL или аргументах командной строки. TLS-проверки включены.
HTTP и WebSocket используют общий проверяющий SSLContext с системными CA и
набором доверенных корневых сертификатов `certifi`. Это также поддерживает
установки Python на macOS без настроенного стандартного CA-файла.
Если возникает `TLS_VERIFY_FAILED`, проверьте сертификат сервера и обновите
корневые сертификаты клиента: `python3 -m pip install --upgrade certifi`.

Логин и регистрация доступны и Python-клиенту. Например, интерактивный запуск:

```sh
python3 frontend/python/asteroidAPI.py --username alice
python3 frontend/python/asteroidAPI.py --username alice --register
```

Пароль вводится через `getpass`. При наличии `ASTEROID_API_KEY` CLI использует ключ.
Python хранит cookie только в памяти; `disconnect()` закрывает сеть, `logout()`
отзывает сессию. Для другого сервера используйте `--server https://...`.

## Контракт протокола

HTTP-запросы отправляются с заголовками `Content-Type: application/json` и
`X-Asteroid-Client: 1`. Python-бот передаёт ключ в `Authorization: Bearer ...`;
сессии используют cookie. При наличии Authorization он имеет приоритет над cookie.
В браузерном WebSocket cookie передаётся при handshake, Python может передать
Authorization. В URL и в каждом игровом сообщении секрет повторять не требуется.

Запрос карты, одинаковый для HTTP и WebSocket:

```json
{"type":"request","request_type":"get_map"}
```

Успешный ответ:

```json
{"ok":true,"result":{"entities":[]}}
```

Ошибка:

```json
{"ok":false,"error":{"status":401,"code":"AUTH_REQUIRED","message":"Войдите в аккаунт."}}
```

Поля операций аккаунта:

| `request_type` | Поля |
|---|---|
| `register`, `login` | `username`, `password` |
| `me`, `logout`, `list_api_keys` | Нет |
| `create_api_key` | `name`, `password`, `expires_days` (1–365) |
| `revoke_api_key` | `key_id` |
| `get_entity` | `entity_id` |
| `get_my_entities` | Нет; владелец определяется только по авторизации |
| `create_craft` | Нет; создаётся корабль текущего пользователя |

`get_my_entities` возвращает `{"entities": [...]}` с полными описаниями объектов,
включая `id`, `owner_id`, `type`, `position`, `velocity` и модули/ресурсы. Сессия и
API-ключ одного пользователя видят один и тот же набор. Переданный клиентом
`owner_id` не меняет фильтрацию. При отсутствии собственных объектов возвращается
пустой массив.

В браузере кнопка «Мои корабли» открывает автоматически обновляемое меню. Нажатие
на строку центрирует карту на корабле и открывает параметры. Кнопка «Создать корабль»
добавляет корабль текущему пользователю и показывает его в списке. Свои корабли на
карте голубые, чужие и серверные — жёлтые; астероиды сохраняют коричневый цвет.
После выхода меню и карта очищаются. Для Python доступна CLI-команда `mine`.

Успех register/login возвращает профиль и устанавливает cookie, но не отдаёт
сессионный токен в JSON. Ошибки всегда имеют единый конверт; HTTP также возвращает
соответствующий статус. WebSocket пока обслуживает запросы последовательно,
поэтому SDK сериализуют отправку/получение. Текстовое приветствие `Your ID: ...`
сохраняется, SDK пропускают его. Старые клиенты без входа больше не подключаются;
после обновления сервера обновите и оба клиента.

## Меры защиты и границы текущей реализации

Пароли хешируются OpenSSL scrypt (`N=2^17, r=8, p=1`) с независимой случайной солью.
Сессионные токены и ключи содержат 256 бит случайности; БД хранит SHA-256-дайджесты,
а не исходные токены. Два рабочих потока выполняют операции аккаунта; вывод паролей
и ключей в логи отсутствует. Хеширование пароля требует около 128 МиБ на операцию
и выполняется вне mutex мира. Нужна память для двух параллельных операций.

Origin проверяется по точному публичному адресу, POST требует JSON и специальный
заголовок, разрешения CORS не выдаются. Для native-клиентов допускается отсутствие
Origin; владение действующим ключом/cookie остаётся обязательным. Backend доверяет
X-Forwarded-Proto и X-Real-IP только за счёт локальной привязки и контролируемого
reverse proxy. Не открывайте backend наружу.

Вход, регистрация и создание ключей ограничены 10 попытками в минуту по IP и
аккаунту; очередь HTTP-запросов ограничена. Отзыв/выход закрывает связанные
соединения, истечение проверяется на каждом запросе и каждые 15 секунд простоя.

Реализованы аккаунты, общая карта, владелец Entity и создание корабля через
`create_craft` с сессией или API-ключом. Модели компаний и экономических правил
создания кораблей ещё нет. Для следующих команд управления потребуется проверять
владельца и отдельные разрешения и для сессии, и для ключа. Восстановление
пароля, подтверждение почты и MFA в этот этап не входят.

## Проверка

```sh
make
make test-auth-ids test-principals
node tests/browser_fleet.test.mjs
```

Тесты используют отдельные временные базы и мир в памяти. Проверяются регистрация,
вход, резервирование ID 0, стабильность указателей Principal, параллельные сессии
и ключи, logout/отзыв, пересоздание AuthStore, рост реестра и создание корабля
через общий диспетчер. Сетевые порты и публичный сервер не затрагиваются.
