# Скрипты судов

Соберите образ `make sandbox-image` и запустите сервер `make run`. Войдите,
выберите своё судно, загрузите `.py`, нажмите «Прикрепить и запустить».
Повторная загрузка заменяет скрипт и останавливает прежний контейнер.
Кнопка «Остановить» останавливает процесс, «Журнал» получает последние 4096 байт
вывода `print()`/traceback. Для безопасного отображения stderr сохраняется как ASCII;
не-ASCII байты заменяются на `?`. Чужие скрипты и журналы недоступны.

Каждый скрипт работает в отдельном контейнере: пользователь 65534, сеть отключена,
корневая ФС только для чтения, host mounts и Docker socket отсутствуют,
capabilities сброшены, `no-new-privileges` включён. Ограничения: 128 МиБ памяти
и swap суммарно, 0.25 CPU, 16 процессов/потоков, 64 дескриптора, tmpfs `/tmp` 8 МиБ,
время работы 1 час, запуск 10 секунд. Максимум 32 одновременно активных скрипта.
Образ не скачивается при запросе игрока (`--pull=never`). Подробнее о параметрах:
[официальная документация Docker](https://docs.docker.com/engine/containers/run/).
Изоляция использует ядро/контейнерный runtime Docker; это не отдельная виртуальная
машина на каждого игрока. Для публичного сервиса с недоверенными пользователями
используйте отдельный Docker-host и усиленный runtime (например, gVisor).

Настройки администратора: `ASTEROID_DOCKER` — путь к Docker CLI (по умолчанию `docker`),
`ASTEROID_SCRIPT_IMAGE` — предварительно собранный образ (`asteroid-python:local`).
Они не принимаются от игроков. На Linux нужен glibc 2.34+ для закрытия наследуемых
дескрипторов через `posix_spawn_file_actions_addclosefrom_np`; macOS использует
`POSIX_SPAWN_CLOEXEC_DEFAULT`. Отсутствие Docker/образа приводит к ошибке запуска,
без перехода на запуск пользовательского кода на хосте.

## Канал связи

В скрипте доступен модуль `asteroid`:

```python
import asteroid

asteroid.send(b'my request')
# Заблокируется до ответа вашего обработчика на сервере:
reply = asteroid.receive()
print(reply)
```

Это только транспорт. Содержание сообщений не интерпретируется, команды игры
и запрос-ответ нужно реализовать самостоятельно. На сервере точка расширения —
`HandleScriptMessage(World&, Craft&, const std::string&)` в `backend/src/game_server.cpp`.
Она вызывается в игровом потоке под `world.mutex` и уже получает конкретное судно,
которому принадлежит отправитель. `std::nullopt` означает отсутствие ответа.
Верните `std::string` с произвольными байтами для ответа либо используйте
`craft.script->Send(bytes)` для инициативного сообщения сервера. Проверяйте возвращаемый
`bool`: `false` означает закрытый канал, превышение размера или заполненную очередь.
Не выполняйте блокирующие операции и не захватывайте `world.mutex` повторно в обработчике.

Внутреннее кадрирование stdin/stdout: `[u32 little-endian: число байт][байты]`.
Максимум 1 МиБ на сообщение в любую сторону, включая пустое сообщение.
Первое сообщение сервера — исходный код UTF-8; первый ответ контейнера — пустой
кадр готовности, служебный и не передаваемый в обработчик. После этого все кадры
пользовательские. `print()` перенаправлен в stderr; не пишите напрямую в `sys.__stdout__`.
До 128 входящих сообщений и 64 КиБ stderr в секунду; очереди ограничены 4 МиБ,
за тик обрабатывается не больше 16 сообщений на судно. Превышение входящих лимитов,
повреждённый кадр или авария завершает скрипт. Обрыв канала сервера завершает контейнер.

Скрипты и исходники живут в памяти вместе с судном, продолжают работать при выходе
игрока, но не восстанавливаются после перезапуска сервера. Неизменяемый код модуля
и entrypoint находятся в `backend/scripts/`; после их изменений пересоберите образ.

После сборки образа `make test-sandbox` проверяет настоящий контейнер: UID,
read-only ФС, запись в tmpfs, отсутствие внешней сети и обмен байтами Python ↔ C++.
Этот тест требует работающего Docker и не входит в обычный `make test`.
